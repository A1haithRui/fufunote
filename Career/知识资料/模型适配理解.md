> **同一个推理框架运行不同模型，不一定要为每个 checkpoint 单独写代码；但只要模型架构、算子、输入模态或并行方式不同，就可能需要新增或修改适配代码。**

更准确地说，适配对象不是“Qwen3 这个名字”，而是它背后的**模型架构和执行特征**。

## 一、Qwen3 和 DeepSeek 为什么可能需要不同适配

假设两个模型只是权重大小不同，但架构完全相同：

```
Qwen3-8B
Qwen3-14B
Qwen3-32B
```

它们通常可以复用同一个模型实现，只是从 `config.json` 读取：

- hidden size
- layer 数
- head 数
- KV head 数
- vocab size
- RoPE 参数

框架不需要为每个规模重新写一套代码。

但如果从 Qwen3 Dense 切到 DeepSeek 这类不同架构，差异可能包括：

- Dense FFN 与 MoE；
- GQA 与 MLA；
- 普通 decode 与 MTP/speculative decode；
- 不同 RoPE 或 attention 机制；
- FP8、INT4 等不同量化格式；
- Expert Parallel 与 All-to-All 通信；
- 特殊权重布局与 checkpoint 命名。

这时就可能牵涉：

```
模型定义
→ 权重加载
→ Attention backend
→ KV Cache layout
→ MoE kernel
→ 并行切分
→ Sampling / Spec Decode
→ CUDA Graph
→ 测试与精度验证
```

vLLM 官方文档也明确指出：新模型若与已有架构相似，适配通常比较直接；若引入新的 attention 或其他新算子，复杂度会明显增加。

因此，“vLLM 能跑 Qwen3”可能只是因为它已经注册并实现了对应架构；并不表示任何新模型权重放进去都天然可用。vLLM 内部确实维护了模型架构注册表，将 Hugging Face 配置中的 architecture 映射到具体实现。

## 二、模型适配通常具体改什么

可以把它拆成六层。

### 1. 配置和模型注册

框架先读取 checkpoint 的配置，例如：

```
{
  "architectures": ["SomeModelForCausalLM"],
  "hidden_size": 4096,
  "num_attention_heads": 32
}
```

然后在模型注册表里找到对应实现。

如果架构名不存在，就需要：

- 新增模型类；
- 注册 architecture；
- 添加示例模型与测试。

### 2. 权重加载与并行切分

Hugging Face 的权重通常不能原封不动塞进高性能推理框架。

适配代码可能需要处理：

- Q/K/V 合并权重；
- gate/up projection 合并；
- Tensor Parallel 分片；
- Expert Parallel 分片；
- 量化 scale；
- checkpoint 参数名映射；
- tied embedding；
- fused parameter layout。

这部分非常容易出现“模型可以加载，但输出错了”。

### 3. 模型 forward 的执行语义

框架需要知道：

- 每层调用什么算子；
- position 怎么传；
- attention metadata 是什么；
- KV Cache 写到哪里；
- MoE router 输出如何 dispatch；
- logits 如何返回。

普通 dense Transformer 可以大量复用已有层；特殊架构则要增加新模块。

### 4. Kernel 和后端支持

模型里出现新算子时，可能发生三种情况：

```
已有高性能 kernel
→ 直接复用

只有 PyTorch fallback
→ 功能能跑，但性能差

完全不支持
→ 需要新增 CUDA/Triton/TileLang kernel
```

比如新的 attention、MoE routing、FP8 GEMM、特殊 normalization，都可能成为适配工作。

### 5. 分布式和调度支持

模型能单卡跑，不代表多卡高效。

还需要考虑：

- TP 怎么切；
- MoE 是否启用 EP；
- 是否需要 AllReduce 或 All-to-All；
- pipeline stage 怎么划分；
- MTP/draft model 怎样调度；
- KV Cache 是否能按新结构管理。

Qwen3 MoE 等模型在不同 TP/EP 配置下，就可能受到权重维度可整除性和量化块大小等约束。

### 6. 正确性和性能验证

适配完至少要验证：

- Hugging Face 与框架 logits 是否接近；
- greedy 输出是否一致；
- 不同 batch/seq length 是否正确；
- TP=1 与 TP>1 是否一致；
- 量化前后精度损失；
- 吞吐、TTFT、TPOT；
- 显存；
- kernel 性能；
- CUDA Graph 和 Prefix Cache 等特性是否正常。

所以模型适配不是“改个配置让它启动”，而是：

> **功能对齐 + 精度对齐 + 性能对齐 + 分布式对齐。**

## 三、文本模型和多模态模型当然有明显区别

文本模型大体是：

```
token_ids
→ embedding
→ language model
→ logits
```

视觉语言模型则通常是：

```
image/video
→ vision encoder
→ projector / connector
→ multimodal embeddings
                    \
text token embeddings
                    /
→ merge / replace placeholder positions
→ language model
→ logits
```

因此多模态适配还需要额外处理：

- 图像/视频预处理；
- vision tower；
- projector；
- multimodal placeholder token；
- 图像尺寸与 patch 数的动态变化；
- 多模态 embedding 如何合入文本序列；
- 多模态输入缓存；
- vision encoder 与语言模型不同的并行策略；
- CUDA Graph 的动态 shape 限制；
- 多图片、多视频的 batching；
- 多模态 LoRA；
- 显存预算。

vLLM 的多模态适配文档就要求模型显式定义占位符、区分语言模型和视觉塔，并实现多模态 embedding 的获取和合并逻辑。

所以：

> **文本模型适配更多围绕 Transformer 主干、KV Cache、并行和 kernel；多模态模型还多出一整条输入编码和跨模态融合链路。**

## 四、你师兄让你研究 SOTA 模型，重点不是“它怎么训练出来的”

训练方法要了解，但不是岗位最关心的第一层。

对于这个“AI 芯片上的模型与框架适配”岗位，你看 SOTA 模型应该始终围绕下面五个问题。

### 1. 它相对传统 Transformer 改了什么

例如：

- Attention 是 MHA、GQA、MLA 还是 sparse/hybrid attention？
- FFN 是 dense 还是 MoE？
- Norm、激活、RoPE 有何变化？
- 是否有 MTP 或 draft head？
- 是否是 multimodal/VLA？

### 2. 这些变化影响了哪些 tensor shape 和数据流

例如 MLA 不能只记“压缩 KV”。

你要追到：

```
输入 hidden state
→ 低秩 latent
→ 如何恢复/使用 K、V
→ KV Cache 实际保存什么
→ head 维度和 cache layout 如何变化
```

MoE 也不能只记 router：

```
token
→ router logits
→ top-k expert
→ token reorder
→ expert GEMM
→ combine
```

### 3. 它对推理系统产生什么影响

重点看：

- KV Cache 大小；
- decode memory bandwidth；
- kernel 数量；
- dynamic shape；
- Prefix Cache；
- CUDA Graph；
- Scheduler；
- speculative decoding；
- batch 能否做大。

### 4. 它对多卡通信产生什么影响

例如：

- MoE 为什么需要 All-to-All；
- expert load imbalance；
- TP 和 EP 如何组合；
- 通信与计算如何 overlap；
- 多节点瓶颈在哪里。

### 5. 在新芯片上最可能缺哪些能力

比如：

- 特殊 FP8 格式；
- fused MoE kernel；
- MLA attention kernel；
- grouped GEMM；
- all-to-all 通信；
- dynamic quantization；
- 特殊 mask；
- vision encoder 算子。

这才是“模型适配工程师”的视角。

## 五、以 DeepSeek 类模型为例，你应该怎么读

不要一上来读完整训练报告。建议按这个顺序：

```
模型配置 config.json
→ 架构图
→ 单层 forward
→ Attention
→ FFN/MoE
→ KV Cache
→ 并行方式
→ 推理特性
→ vLLM/SGLang 实现
→ kernel 和通信
→ 精度/性能测试
```

每个模型最终产出一张表：

|维度|需要回答|
|---|---|
|基础结构|Dense/MoE、层数、hidden、heads|
|Attention|GQA/MLA/sparse/hybrid|
|FFN|Dense、MoE、top-k、shared expert|
|推理特性|KV Cache、MTP、长上下文|
|并行|TP/EP/PP|
|Kernel|GEMM、attention、MoE、quant|
|通信|AllReduce/All-to-All|
|框架适配点|model class、weight loader、backend、scheduler|
|芯片风险|不支持算子、精度、性能、显存|
|验证|logits、generation、E2E、kernel|

这张表就是你之后投达摩院时最有用的“模型理解”。

## 六、你明天在昇腾设备上可以做什么

不要直接写“适配了某模型”。先做一个真实小闭环：

1. 选择一个已支持的 Qwen 文本模型；
2. 确认 vLLM-Ascend 版本与模型支持；
3. 部署并验证 greedy 输出；
4. 做 batch、input length、output length 测试矩阵；
5. 记录 TTFT、TPOT、吞吐、显存；
6. 找到一个限制或异常；
7. 追踪它位于模型、框架、算子还是硬件层；
8. 尝试最小修改或参数调优；
9. 重新测试。

然后再换成：

- Qwen MoE；
- 多模态 Qwen；
- 量化版本；

比较适配难度到底多在哪里。

这样你会从“部署过模型”走向：

> **我能分析不同模型架构对推理框架和芯片后端的要求。**

你今晚的判断也挺准确：很多秋招简历不是靠惊天创新，而是靠一个真实、完整、能被追问的技术闭环。你现在正在形成的主线已经很清楚了：

> **SOTA 模型结构 → 推理框架实现 → 异构芯片适配 → 功能/精度/性能定位。**

这条线比单独背 vLLM 八股更贴达摩院这个岗位。

模型为什么这样算

## 第一层：模型结构

先建立一条清楚的演进线：

```
标准 Transformer
→ MQA / GQA
→ MoE
→ MLA
→ MTP / 投机解码
→ 多模态模型
→ VLA
```

每个模型只回答五个问题：

1. 相比普通 Transformer 改了什么？
2. forward 数据流怎么走？
3. tensor shape 怎么变化？
4. 对 KV Cache、通信和显存有什么影响？
5. 框架需要新增什么支持？

所以你研究 DeepSeek、Kimi，不是主要研究训练语料和训练技巧，而是研究它们对框架提出了什么新要求。

## 第二层：框架适配

以 vLLM 为主线，真正跟一遍新模型如何接进去：

```
config / architecture 名称
→ model registry
→ model class
→ layer 与 forward
→ weight loader
→ tensor parallel 切分
→ attention backend
→ KV Cache
→ quantization
→ sampling / speculative decoding
→ correctness tests
```

最好实际选一个已有模型，沿着代码回答：

- 它在哪里注册？
- Hugging Face 权重如何映射？
- QKV、gate/up 是否合并？
- TP 后每张卡拿哪些权重？
- 使用哪个 attention backend？
- 哪些模块是复用，哪些是模型专属？
- 如果放到昇腾上，调用路径在哪里变化？

这比泛泛地读完整 vLLM 更贴岗位。

## 第三层：芯片与性能定位

这时性能分析工具才真正接上。

适配中遇到问题，可以分成三类：

- **功能问题**：算子缺失、shape 不支持、动态图逻辑错误、模型无法加载。
- **精度问题**：权重映射错误、量化 scale 错误、算子数值差异、通信或并行切分错误。
- **性能问题**：fallback、频繁同步、小 Kernel、内存访问差、通信阻塞、算子未融合。

你需要逐渐形成这种诊断顺序：

```
先验证输出
→ 再定位模型层或算子层
→ 再看框架执行图
→ 再用 profiler 看 Kernel 和通信
→ 最后提出优化
```

而不是一上来就开 Nsight 看一堆时间线，却不知道哪些 Kernel 本来就不该出现。
