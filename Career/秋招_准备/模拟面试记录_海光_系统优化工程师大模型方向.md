## 三、环节二：开场与岗位理解（5–12 min）

**面试官：** 这个 JD 第一条就是"大模型训练与推理性能分析"。我先问个实际的：线上有人反馈大模型服务变慢了，你作为系统优化工程师，一上来会怎么定位？是先看代码，还是先跑 benchmark，还是直接开 profiler？

**候选人：** 我不会一上来就开 profiler，那样容易掉进"局部细节"里。我会先做三件事：
1. **把问题量化清楚**：是 TTFT 变慢、TPOT 变慢、整体吞吐掉，还是 P99 尾延迟变差？有没有具体的请求长度、batch、并发、模型版本？没有指标就没有优化。
2. **先看端到端时间分片**：一个请求从进入调度器到返回，先切成 prefill、decode、采样、调度等待、数据传输、数据加载等几段，看时间到底花在哪一段。
3. **再决定用什么工具深挖**：如果是 GPU kernel 内部慢，用 PyTorch Profiler / hipprof / nsys 看 kernel 耗时；如果是等待和空闲，说明瓶颈在调度、通信或数据加载，这时候要拉 timeline 看 GPU 有没有饿着。

所以我习惯的口径是：**先用粗粒度数据确认方向，再用 profiler 往细里定位**，最后用一个小实验验证改动。

**面试官：** 那在一个 CPU+GPU 异构环境里，你怎么判断瓶颈到底在 CPU 侧还是 GPU 侧？

**候选人：** 核心看"GPU 是不是一直在干活"。如果 GPU 利用率很高、kernel 时间占比也高，那瓶颈大概率在 GPU 计算/访存；如果 GPU 利用率不高，但 CPU 侧已经跑满，或者 timeline 上 GPU 一段忙一段空，那通常就是 CPU 侧的数据加载、Python 开销、调度器、或者通信没喂饱 GPU。具体我会看三类证据：
- **GPU timeline 上的空闲缝隙**：比如两次 kernel 之间有长 gap，说明有等待；
- **CPU 侧的开销**：用 perf 看 Python/C++ 热点，或者看数据加载线程和 frontend 是不是阻塞；
- **队列与吞吐的匹配**：比如 dataloader 的吞吐低于 GPU 的消费速度，那就是数据加载瓶颈。

在昇腾上我会分两层：
- 先用 `npu-smi` 看卡级状态：AI Core 利用率、HBM 占用、温度、功耗这些，适合判断"卡有没有在干活、显存是否吃紧、有没有降频"；
- 再往下就要用 CANN 的 `msprof` 或 `torch_npu.profiler` 拿**算子级/内核级 timeline**，看每个算子的耗时、AI Core 利用率、内存拷贝、通信耗时和任务调度空隙，才能定位到具体是哪个算子、哪段通信或哪个 CPU 等待拖慢了整体。
在 NVIDIA 上对应的就是 `nsys` + `ncu`。方法是一样的：**找等待、找热点、算上界**。

**面试官：** 说得还挺清楚。那咱们开始聊项目，先聊华为那个 AWQ。

## 四、环节三：项目拷打（一）——华为 vllm-Ascend AWQ 量化插件（12–28 min，重点）

### 4.1 项目整体

**面试官：** 用两分钟把这个项目完整讲一遍：背景是什么，你负责什么，最后交付了什么？

**候选人：** 背景是：我们想在昇腾 910B 上用 vLLM 跑 Qwen3-8B 这类模型做在线服务。FP16 权重能让模型跑起来，但显存和带宽都吃紧，业务希望上 INT4。昇腾自己有量化路径，但精度和生态融入一般；而且我们希望尽量复用 vLLM 主线的量化机制，让 checkpoint、加载、kernel 调用跟社区一致。

我的工作概括成一句话：**把 AWQ 方法在昇腾 + vllm-ascend 上落地成一个可注册、可加载、可跑的量化插件**。拆开是四条线：
1. 用 PyTorch 把 AWQ 的算法流程写出来：激活感知的 scale 搜索 + 权重裁剪，先离线把 Qwen3-8B 的 252 个 Linear 层量化好并验证精度；
2. 深入 vLLM / vllm-ascend 的 quantization pipeline，搞清楚量化方法如何注册、checkpoint 如何加载、kernel 如何被调起来，然后注册自定义方法 `awq_ascend`；
3. 解决 checkpoint 加载里 QKV、Gate-Up 等参数命名映射问题；
4. 结合 Marlin 这类 weight-only quantized GEMM 的执行范式，梳理"离线量化 → packed weight → 运行时反量化 → GEMM"的分层关系，把昇腾侧的数据契约对齐。

交付物包括：离线量化脚本、`awq_ascend` 集成、Qwen3-8B 与 Qwen3-30B-A3B 的量化模型、以及一组精度和性能验证数据。

### 4.2 AWQ 原理拷打

**面试官：** AWQ 叫"激活感知"，那激活到底怎么参与？它跟"挑权重绝对值大的 channel 保护"有什么本质区别？

**候选人：** 区别很大。直觉上大家容易觉得"重要的权重是数值大的"，但 AWQ 的观察是：量化误差对每个 output channel 的影响，主要取决于这个 channel 经常被多大的激活打。如果一个 channel 对应的激活值经常很大，那这个 channel 的权重稍一出错，输出误差就会被放大。所以 AWQ 里"显著权重"的定义是**激活感知**的：拿一小部分校准数据过一遍模型，统计每个 channel 的激活幅度，激活大的 channel 被认为是重要的。

做法上也不是"重要 channel 保留高精度"，那样会破坏 GEMM 的整齐性。AWQ 的做法是给这些 channel 的权重乘一个大于 1 的 per-channel scale，把权重数值压小，在同样量化步长下减少相对误差；然后把这个 scale 数学等价地吸收到下一层线性层里，推理时权重依然是整齐的 INT4 + 反量化，不需要额外分支。

**面试官：** scale 是搜出来的？怎么搜的？

**候选人：** 对，是搜索出来的，不是手调。AWQ 把每个 channel 的 scale 参数化成一个候选集合，比如 `s^x`，x 在 0 到 1 之间做网格搜索，对每个候选 scale 计算该层量化前后的输出误差（我们用的是 MSE），取误差最小的 x。这样搜索空间不大，但比固定 per-channel scale 效果好很多。我们基本沿用这个做法，校准数据根据业务语料做了一些调整。

**面试官：** 光说搜索不够，我想听点你实际写代码踩过的坑。有没有一开始 scale 搜索完全没效果的情况？为什么？

**候选人：** 有，第一版我把整个 group 乘同一个标量 `s`，结果所有候选的重建误差完全相同，提升 0.0%。原因是对称 group 量化下：
`round(w·s / (s·max|w|/7)) = round(w·7/max|w|)`，
s 在分子分母抵消了。也就是说只要缩放是"组内统一的标量"，量化决策就和 s 无关。所以 AWQ 的 s 必须**逐输入通道**，让 W·s 改变组内相对分布，组 max 变化，量化粒度才真正变化。
另外一个坑是 weight clipping：clip 必须在**已 scale 的权重 W·s** 上搜索，而且校准激活要传 `X/s`，因为 AutoAWQ 的 `apply_scale` 是同时做 `W·s` 和 `inp/s`，这样搜索目标才是真实输出 `X·W^T`。我第一次把 clip 用在未 scale 的 W 上再套到 W·s 上，误差直接暴涨 +430%。

**面试官：** 简历里写"252 个 Linear 层量化误差平均降低 55.3%"，这个数字怎么算的？跟谁比？

**候选人：** 基线的 RTN —— round-to-nearest，就是直接就近舍入、不做任何保护。55.3% 的意思是：在同样 INT4 位宽下，AWQ 相对 RTN，这 252 个 Linear 层的输出误差平均相对下降 55.3%。这个量级和社区报告基本吻合。然后全模型量化后和 FP16 原始模型比对 logits 余弦，Qwen3-8B 是 0.9989。这两个指标一个看单层，一个看端到端，互相印证。

### 4.3 昇腾上的执行路径与 Marlin 范式

**面试官：** Marlin 是 NVIDIA 的 kernel，昇腾又没有 Marlin。你说"结合 Marlin 执行范式"到底落在哪？昇腾上实际的 GEMM 是谁在跑？

**候选人：** 这个问题我得诚实回答：**kernel 主体不是我写的**，昇腾上的 INT4 GEMM 走的是 vllm-ascend 已有的算子路径。我做的是把数据契约对齐。Marlin 这套范式有一个很清晰的层次：checkpoint 里权重怎么 pack、运行时怎么反量化、反量化和 GEMM 怎么衔接。我把它梳理成"离线量化产出 packed weight → 加载时按 runtime 需要的 layout 重新打包 → 运行时反量化（可以在寄存器里顺带做）→ 进入 GEMM"这条链路，然后看昇腾 kernel 期望的输入格式，把 checkpoint 解析和格式转换做到两边一致。

Marlin 本身我是理解的：它是 weight-only 4-bit GEMM，把 INT4 打包进 int32，用 tile 化利用 Tensor Core，反量化尽量在寄存器里完成，减少访存。我们借的是它的"思想"和数据流，昇腾 kernel 是昇腾自己的。

**面试官：** 那 vLLM 的 quantization pipeline 具体长什么样？你要注册一个自定义方法，动了哪些东西？

**候选人：** vLLM 里量化是声明式的：模型 config 的 `quantization_config` 里写 method 名，比如 `awq`；vLLM 根据这个名字从注册表找到对应的量化实现类，之后 weight loading 和 kernel 调用都走这个类约定的接口。核心有一类 `WeightOnlyQuantConfig`，它声明 weight 的打包方式、量化粒度（比如 per-group 128）、以及哪些层要被量化。

我要加自定义方法，主要做两件事：一是加载侧，把 AutoAWQ/HF 格式的 checkpoint 解析成 vLLM 内部表示，再按昇腾 kernel 要的 layout 重新 pack；二是执行侧，在算子调用点接到昇腾的 kernel 路径上去。命名上我们注册的是 `awq_ascend`，这样 config 里写这个名字就能走通整条链路。

**面试官：** 我看你实际 checkpoint 里每个量化 Linear 存了 `qweight`、`qscales`、`awq_scale` 三个张量。为什么不直接存反量化后的权重？`awq_scale` 还存成 `[1, in]` 而不是 `[in]`，这又是为什么？

**候选人：** 三个张量各司其职：
- `qweight` 是 `Q(W·s)` 的打包结果，`[out, in/8]` int32，每个 int32 按低 nibble 先装 8 个 int4；
- `qscales` 是 `W·s` 的逐 (输出行, group) 对称量化 scale，`[out, in/128]`；
- `awq_scale` 是 AWQ 的逐输入通道 scale s。

不直接存反量化权重，是为了保持真正的 INT4 存储收益；运行时 `process_weights_after_loading` 里再解包乘 qscales，得到近似的 `W·s` 作为 dequant weight。这里有个细节：dequant 结果我存成 **bf16** 而不是 fp32，否则 8B/30B 的 dequant 权重会多占一大块显存，单卡 64GB 在 `gpu_memory_utilization=0.6` 下容易 OOM；bf16 舍入相对 INT4 量化误差可以忽略。

`awq_scale` 存 `[1, in]` 是因为 vllm-ascend 的 `AscendLinearMethod` 会给所有参数统一打上 `input_dim=1, output_dim=0`。ColumnParallelLinear 沿 output_dim=0 narrow，RowParallelLinear 沿 input_dim=1 narrow；如果 `awq_scale` 是 1D `[in]`，Row 路径里 `shape[1]` 会越界。存 `[1, in]` 后两条路径 narrow 都是对自身做 no-op，而且 apply 里和 `x` 广播也兼容。

推理语义是 `out = linear(x / awq_scale, dequant)`，也就是 `(x/s)·(W·s)^T ≈ x·W^T`。

**面试官：** 你为什么不把 `awq_scale` 像 AutoAWQ 社区格式那样折进前一层权重里？那样 checkpoint 更省。

**候选人：** 因为我同时控制保存器和插件，逐层自包含地存 s 更简单、更不容易错，不需要跨层簿记，也不用给首层额外加 ScaledActivation。数学上两者等价：`x·(dequant(Q(W·s))/s)^T` 和 `(x/s)·dequant(Q(W·s))^T` 是一样的。等以后接真 INT4 GEMM，也可以再考虑把 `1/s` 折进权重或上一侧激活，那是性能优化，不是正确性问题。

### 4.4 参数映射坑

**面试官：** 你特别提到"基于参数映射解决 QKV/Gate-Up 命名问题"。展开说说，这个坑到底长什么样？

**候选人：** 这个坑非常典型。HF 的 checkpoint 里，Qwen 的注意力是 `q_proj / k_proj / v_proj` 三个独立张量，FFN 是 `gate_proj / up_proj` 两个独立张量；但 vLLM 为了跑 fusion kernel，在加载时会把它们拼成 `qkv_proj`、`gate_up_proj` 这种一个张量，并且按特定列顺序拼接。如果只按名字一一对应，`q_proj` 可能会找不到，或者放错列的位置——最坑的是放错位置还不一定报错，模型能加载、能跑，但输出是垃圾。

我的做法是建一张参数映射表："HF 参数名 → vLLM 融合张量 + 列偏移"。比如 `q_proj` 对应 `qkv_proj` 的第 0 到 hidden 列，`gate_proj` 对应 `gate_up_proj` 的前半段。先把单头权重读出来，按融合布局拼进去，最后用一个小的数值对齐用例兜底：单层输出跟 PyTorch reference 对余弦，对不上就说明映射拼错了。昇腾侧因为后端有自己的融合策略，命名差异比标准 vLLM 还多一点，这张表也把这些差异覆盖了。

**面试官：** 这个映射坑具体是 vLLM 的 `stacked_params_mapping` 子串匹配吧？你实际踩到的报错长什么样？

**候选人：** 对，vLLM 的 `Qwen2DecoderLayer.load_weights` 里 `stacked_params_mapping` 是**子串判断**：`if weight_name not in name`，也就是说只要名字里包含子串就误路由。我们连续踩了两个 fused 名：
- `gate_up_proj.*` 里面含 `up_proj` 子串，会被误路由成 `gate_gate_up_proj.*`，直接 KeyError；
- `qkv_proj.*` 里面含 `v_proj` 子串，会被误路由成 `qkqkv_proj.*`，同样 KeyError。

所以最终 checkpoint 不能存 fused 名，必须存**分离的 HF 名** `q_proj/k_proj/v_proj/gate_proj/up_proj`，让 `stacked_params_mapping` 按 shard_id 正常路由到 qkv/gate-up 融合参数里。这个坑不报错还好，报错反而是幸运的——最怕的是子串撞上但没 KeyError，权重放错列，模型能跑但输出是垃圾。

### 4.5 MoE 量化拷打

**面试官：** 下一个重点：Qwen3-30B-A3B 的 MoE INT4 量化。MoE 量化难在哪？不要背概念，说你实际碰到的。

**候选人：** 实际碰到两个点最痛。一是**专家权重的"训练不充分"**：每个专家只被路由到它的那部分 token 训练，所以专家权重分布和 dense 模型不太一样，有些专家分布很"怪"，量化容易崩。二是**校准数据的归属问题**：如果拿全部校准 token 对每个专家做激活统计，统计出来的是全局分布，但每个专家实际只吃到被 router 分给它的那部分 token。比如 128 个专家里，某个专家可能只被 5% 的 token 激活过。

所以我把校准改成**逐专家校准**：对每个专家，只收集校准集里真正被 router 分给它的 token 子集，用这个子集做激活统计、做 scale 搜索。这个改动对误差的贡献非常直接。

**面试官：** "校准阶段碎片化 OOM"怎么定位到是碎片，而不是单纯显存不够？

**候选人：** 单卡 64GB，校准时要前向收集所有专家的激活统计，中间结果全堆在 GPU 上，峰值叠到 60G 以上；更麻烦的是校准循环里反复创建、释放各种不同尺寸的中间 tensor，PyTorch 缓存分配器会把显存切成很多小洞，后面一个大 tensor 分配不下就 OOM。判断是碎片的方法：OOM 时用 `npu-smi` 看已用显存，只有 45G 左右，峰值也就 60G 出头——总量其实够，那就是碎片。

解法两个：一是把校准用的 activations 搬到 CPU（calibration activation CPU offload），GPU 上只留必要的；二是给每个专家用"固定行数"的统一缓冲区，提前一次性分配，避免按每个 batch 的 token 数动态扩缩造成反复分配和碎片。这么处理之后峰值降下来，OOM 没有再出现。

**面试官：** 62GB 压到 17.8GB，约 3.5 倍。为什么不是 4 倍？数学上 30B 模型 INT4 不应该是 15GB 吗？

**候选人：** 好问题，15GB 是"纯权重、零开销"的理想值。实际做不到有这么几个原因：
- 我们做的是 weight-only 量化，每个 group（比如 128 个权重）还要陪一个 FP16 scale，摊下来每权重多 0.125 bit；
- embedding、norm、router 这类模块我们保持高精度，不量化，也要占显存；
- MoE 模型里除了专家权重，还有门控、共享 expert 等结构；
- 文件/加载格式可能还要对齐、填充，不是理想的连续二进制。

所以 62 到 17.8 的 3.5 倍，和"INT4 + per-group 开销 + 部分模块不量化"的账是对得上的。全量化且无 scale 的理想情况才接近 4 倍。

**面试官：** 我注意到实际 MOE checkpoint 每层用的是 `w13_qweight / w13_qscales / w13_awq_scale / w2_qweight / w2_qscales / w2_awq_scale` 六个 fused 3D 张量，而不是 128 个专家分开存。为什么这么设计？

**候选人：** 一开始我也考虑过 per-expert 分离，但被 vLLM/vllm-ascend 的加载契约卡住了：
1. `register_parameter` 不允许参数名带点，`experts.w13_.qweight` 这类 per-expert 名在 PyTorch 里物理不可行；
2. `experts.gate_up_proj.*` 这种 fused 名会触发 `Qwen3VLMoe.load_weights` 里为未量化 3D 权重设计的 transpose+chunk，会把我的打包布局打乱；
3. generic 分支对未命中 mapping 的权重只调 `weight_loader(param, loaded_weight)` 两参，而 `FusedMoE.weight_loader` 是六参，直接挂会炸。

所以最终直接采用 FusedMoE 层的参数名：`mlp.experts.w13_*` / `w2_*`，六张 fused 3D 张量，配合 `load_whole_tensor=True` 让 adapter 把 weight_loader 换成 `default_weight_loader`，整张拷贝。这样加载路径最简单，也绕开了所有子串和参数名陷阱。

**面试官：** 你这个 MoE scheme 的 `apply` 是逐 expert 循环的 torch 兜底，性能肯定不行吧？这块你怎么收尾？

**候选人：** 对，那个 `apply` 是**正确性优先**的验证实现，不是生产实现：48 层 × 128 专家逐 expert 做 unpack + 反量化 + 小 GEMM + scatter，生成 19 个 token 大约要 11.7 秒，非常慢。我当时用它完成数值验证，证明量化格式、加载和路由语义是对的。生产要走 vllm-ascend 已有的 `W4A16 fused_experts` 算子路径，需要把我们的 checkpoint 重新打包成算子期望的 `[num_experts, ...]` packed layout，让真正的高性能 GMM 去跑。这是我在项目复盘里明确写的下一步，不是已经做完的东西。

**面试官：** 除了加载格式，实际在 vLLM 0.21 里跑 MoE 的时候，自定义量化还容易踩哪些"接口契约"坑？

**候选人：** 我踩了两个很典型的：
1. **`get_quant_method` 必须接收 `tid2eid` 关键字**：vllm-ascend 的 `AscendFusedMoE.__init__` 会以 `get_quant_method(self, layer_name, tid2eid=self.tid2eid)` 调用，我最初签名没有这个参数，直接 `TypeError: unexpected keyword argument 'tid2eid'`；
2. **`scheme.apply` 必须返回 `FusedExpertsResult` 而不是裸 Tensor**：层级 `forward_impl` 在 apply 之后访问 `fused_experts_results.routed_out`，我一开始返回裸 Tensor，报 `AttributeError: 'Tensor' object has no attribute 'routed_out'`。tp=1 时 `routed_out=out` 就是最终结果，包一层就行。
这两个坑都在源码里写得清清楚楚，但只有真正跑到 forward 才会暴露，属于"文档再详细也容易漏"的接口契约。

### 4.6 vllm-ascend W4A16 真 INT4 GEMM 算子路径（生产化方向）

**面试官：** 你说生产要走 vllm-ascend 已有的 W4A16 `fused_experts` 路径。可以展开讲讲，这条真 INT4 GEMM 路径在 vllm-ascend 里到底是怎么跑的吗？它和你那个 torch 兜底的本质区别是什么？

**候选人：** 可以。vllm-ascend 里现成的真 INT4 MoE 路径在 `quantization/methods/w4a16.py`，它对应的是 LLM-Compressor 格式的 W4A16，不是我的手写 AWQ 格式，但算子执行链路是共用的。链路大致是：

1. **加载后重排布局**：`process_weights_after_loading` 里把 checkpoint 里的 `w13_weight_packed / w2_weight_packed` 先 `unpack_from_int32` 还原成 int8 的权重，再转置成算子想要的 `[num_experts, hidden, 2*intermediate]` / `[num_experts, intermediate, hidden]` 这类形状，最后用 `torch_npu.npu_convert_weight_to_int4pack` 重新打成 NPU 的 int4pack 布局。同时把 scale/offset 也转置到对应 layout。
2. **路由 dispatch**：`apply` 里先 `select_experts` 算 top-k，然后进入 `moe_comm_method.fused_experts()`，由 `token_dispatcher` 做 token→expert 的 permute/dispatch。
3. **真正的 GMM 计算**：`quant_apply_mlp` 里走 `torch_npu.npu_grouped_matmul`，并传入 `antiquant_scale` 和 `antiquant_offset`。如果是 fusion 打开的场景，第一层 gate/up 会走 `npu_grouped_matmul_swiglu_quant` / `grouped_matmul_swiglu_quant_weight_nz_tensor_list`，把 GMM1 和 SwiGLU 激活融合掉；第二层 down_proj 再走 GMM2。最后 `token_combine` 按路由权重把各专家结果加权求和。
4. **返回契约**：包成 `FusedExpertsResult(routed_out=...)` 返回给上层。

和我的 torch 兜底比，本质区别是：**torch 兜底是在显存里把每个专家的 INT4 解包、反量化成完整的 bf16 权重再 `F.linear`**，所以又占显存又慢；真 INT4 路径是让 NPU 算子直接吃 int4pack + scale + offset，在 GMM 内部做 online dequant，不落一个完整 bf16 权重矩阵。这样既省带宽又省显存，才是 INT4 该有的收益。

**面试官：** 那如果要把你的 `awq_ascend` MoE checkpoint 接到这条真 INT4 路径上，具体要做哪些转换？

**候选人：** 主要做三件事：
1. **格式转换**：我的 checkpoint 是目前逐专家 `w13/w2_qweight + qscales + awq_scale` 的低位先打包格式，需要先 unpack 成 int8，再做 transpose，最后用 `npu_convert_weight_to_int4pack` 重打成算子需要的 NPU int4pack 布局；
2. **scale/offset 对齐**：我的 `qscales` 是 `[num_experts, out, in/group]`，`awq_scale` 是逐 expert 的输入通道 scale。要么在算子前把激活侧先除以 `awq_scale`，把 AWQ 的 `s` 从激活侧消掉，然后把 `qscales` 转成算子要求的 `[num_experts, hidden/group, 2*intermediate]` 这类 scale layout；要么就把 `1/s` 进一步折算进 scale/offset 里，具体看算子支持哪种语义；
3. **接入 adapter**：在 `AscendFusedMoEMethod` 的 `process_weights_after_loading` 里完成上述 repack，`apply` 从逐 expert torch 循环改成调 `moe_comm_method.fused_experts`，并返回 `FusedExpertsResult`。
这块我明确是“未完成的生产化 TODO”，面试里我会说清楚：正确性链路已经走通，性能链路知道怎么接，但没有在实习期内做完。

### 4.7 精度与性能指标拷打

**面试官：** 你简历里有几个数：纯文本 logits 余弦 0.98，多模态 0.85，argmax 保持率 97.5%。这三个数怎么理解？多模态为什么差这么多？

**候选人：** 口径说一下：logits 余弦是量化后模型和 FP16 模型在测试集上的 logits 相似度；argmax 保持率是"逐位置预测的 token 和 FP16 完全一致"的比例。

单看 97.5% 好像很高，但生成是自回归累积的，每步 2.5% 的差异会滚雪球，长文生成几百步，几乎没有一条完整回答能和 FP16 完全一致。所以我们真正关注的是 logits 余弦和下游质量，argmax 只是一个快照指标。

多模态 0.85 确实比预期差。事后分析有两层：一是视觉编码器对数值精度更敏感，视觉 token 的分布和文本差异大，INT4 误差在视觉分支上会被放大；二是多模态评测里一个视觉 token 算错影响整段生成，不像文本那样误差局部化。当时优先级是保文本质量，多模态的评估做浅了，这是我复盘里明确的一条。

**面试官：** 多模态 0.85 这个结论听起来像"事后归因"，你有没有做过控制实验，把 vLLM/HF 两端差异和量化误差分开？

**候选人：** 做了，而且这个分离我花了不少功夫。我先用同一个脚本、同一批 5 张图，跑 **Qwen3-VL-8B 未量化模型**：vLLM-bf16 vs HF-bf16，逐图平均 logits 余弦是 **0.9936**，说明 vLLM 和 HF 两端多模态预处理/embedding 差异只造成约 0.6% 的 logits 损耗。所以 30B 量化端从纯文本 0.98 掉到多模态 0.8524 的额外 ~0.13 损耗，主要责任基本可以归到 AWQ INT4 量化对视觉激活分布覆盖不足，而不是框架差异。

**面试官：** 那你有没有试过用多模态数据补充校准集来改善 0.85？

**候选人：** 试过，而且做了三版对照：
- 纯文本校准：0.8524；
- 纯文本 + 8 张手绘几何图（image token 占比约 17%）：0.8427；
- 仅 8 张几何图（占比约 89%）：0.8149。

三版都没有改善，这其实**证伪了"image/text token 占比错位"的假设**。最终归因是：AWQ 单组 scale 对 image/text 两种激活分布共存本质是个折中，任何单一分布校准都会牺牲另一种；而且手绘几何图形太同质，不能代表真实图像分布。要真正解决，要么用真实多样的照片级数据，要么做 image/text 分离 scale，但这已经超出原始 AWQ 算法能稳定覆盖的范围。所以 0.85 我认，但它不影响"量化后行为保持"这个结论。

**面试官：** "高并发场景吞吐提升 80%"怎么测的？提升到底从哪来？量化是 4 倍省带宽，为什么只拿到 80%？

**候选人：** 口径先说清楚：对比的是业务目标场景下（比如 64 路并发、长短 prompt 混合）"FP16 + 量化前"和"INT4 + 量化后"的端到端吞吐（tokens/s），80% 是这个口径下的相对提升。

来源拆两块。第一块是直接带宽收益：decode 阶段每步要读全部权重，是典型的 memory-bound，权重从 FP16 变 INT4，读带宽需求降 4 倍，理论上限很高。第二块是间接收益：显存占用降下来后，同样的卡能开更大的 batch，调度更舒展，吞吐也跟着涨。

为什么不是 200%？因为瓶颈转移了：带宽不再是唯一瓶颈，后面可能卡在算子效率、batch 上限、TP 通信、采样开销等地方；而且 KV cache 没有量化，长上下文场景 KV 显存占比会回升。80% 是"业务真实负载下的净收益"，不是 kernel 峰值收益。

**面试官：** 做性能提升怎么保证你的 benchmark 是可复现的？比如 80% 这个数，别人拿过去能不能复现？

**候选人：** 我能给到四个层面：一是**固定环境**，模型版本、vLLM/vllm-ascend commit、CANN 版本、驱动、卡型号全部记录；二是**固定负载**，用固定的 prompt 集合、固定的输入长度分布和并发数，最好把 requests 文件也留下来；三是**实验流程**，先 warmup 再正式测，每组跑多次取稳定值或中位数，同时记录 P99 而不是只看均值；四是**过程数据**，保存 GPU 利用率、显存、吞吐的采样曲线，不只给一个最终数字。这样别人重跑，至少能确认环境一致和负载一致，差异大多能定位到软硬件版本。

## 五、环节四：项目拷打（二）——InfiniLM 调度优化与模型适配（28–42 min）

**面试官：** 第二个项目。InfiniLM 是你们组自研的 C++ 推理框架？它的定位是什么？你具体啃了哪两块？

**候选人：** 对，是组内自研的服务端 C++ 推理框架，面向高并发在线服务，整体结构是"调度器 + 显存管理 + 算子层"。我主要负责两块：一是调度器侧的 P/D 优化，二是 DeepSeek-V4 Mini 1B 的适配和数值对齐。

**面试官：** "P/D 共用 max_batch_size 导致调度瓶颈"具体是什么现象？为什么共用 max_batch_size 是错的？

**候选人：** 现象很典型：高并发 + 长输入场景下，来一波长 prompt 的 prefill 请求，一下子把 batch 上限占满，后面 decode 中的请求全被堵着排队，TTFT 和 P99 直接爆掉。根子有两处：一是 prefill 和 decode 共用一个 batch 上限，但一个 prefill 的算力消耗可能是几十个 decode 的量级，等于"一个胖子占了十个座位"；二是原调度逻辑太简陋，基本是 FCFS，一个请求不跑完不腾位置，导致 GPU 利用率忽高忽低。

我的改动两条：**连续批处理**——只要有空 slot 就插入新请求，被抢占/暂停的请求做好状态保存、后续恢复执行，把"一个请求独占到结束"改成"迭代级调度"；**chunked prefill**——把长 prefill 拆成小 chunk，插进 decode 的空隙去跑，避免一个大 prefill 长期霸占 GPU。

**面试官：** 这不就是 vLLM 在做的事吗？你是抄 vLLM，还是有自己的东西？

**候选人：** 概念同源，但落地全是自己的：框架是 C++ 自研，有自己的显存管理和调度器，没有代码可抄。真正的差别在两点：
1. 我们当时的 KV cache 管理不算彻底 paged，chunked prefill 是按整块 KV 分配的，所以 prefill chunk 不能切太小，否则 KV 分配开销会吃掉收益；
2. 为了支撑打断/恢复，我给请求补了 token 级状态机，调度器要记住"这个请求 prefill 到第几个 token、停下来时 KV 在哪个块"。这块细节工作比想象中多。

**面试官：** 那"混合 P/D 批次"呢？vLLM 社区主流观点是 prefill 和 decode 分开跑，因为混在一起 prefill 会把 decode 延迟打爆，你为什么反而做混合？

**候选人：** 这是吞吐和延迟的权衡。社区建议分开，是因为 prefill 是重计算操作，跟 decode 抢算力会把小 batch decode 延迟打高。但我们当时在**纯文本模型**上实测发现：decode 阶段 GPU 大量空闲——decode 计算强度低、主要吃带宽，而 prefill 刚好能把空闲算力填起来，混着跑对小 batch decode 延迟伤害不明显，吞吐收益很直接。

当然不是无脑混，我们做了控制：prefill chunk 大小根据当前 decode 负载动态调整——decode 少、有空闲算力时给 prefill 大 chunk，反之就压小，避免在大批量 decode 时被 prefill 抢算力。另外**多模态模型我们选择分开**，因为视觉编码器一般要一次性把整图序列跑完，没有合适的 chunk 空间，混不了。纯文本可以混的本质是 prefill 和 decode 的资源画像不同、能互补。

**面试官：** 78% 的吞吐提升和华为那个 80%，测法一样吗？

**候选人：** 口径不完全一样。华为那边是"量化前后"对比；这边是"调度优化前后"对比：同样模型、同样负载（高并发长短混合），优化前是原 FCFS 调度，优化后是连续批处理 + chunked prefill + 混合 P/D，端到端吞吐提升 78%。主要来源是 GPU 空闲被填满 + 长 prefill 不再堵车。

**面试官：** 调度优化最容易把模型输出改坏，你们怎么保证优化后精度没有回退？

**候选人：** 我们做了三层回归：
1. **数值回归**：同一组 prompt，优化前和优化后跑推理，对比 logits 和输出 token 分布，调度逻辑不应该改变任何数学计算，所以数值应当完全一致；
2. **长序列稳定性测试**：重点覆盖长输入 + 高并发 + 抢占恢复场景，确认恢复后的输出和未抢占时的输出一致；
3. **端到端业务指标**：在真实负载上跑一小段时间，看返回质量相关指标有没有异常。
因为调度优化动的是"什么时候算、分几段算"，不应该动"怎么算"，如果发现数值不一致，那一定是有状态保存/恢复 bug。

### 5.4 深水区：如果被问 vLLM Scheduler 源码对比

**面试官：** 你既然说自己做了连续批处理和 chunked prefill，那应该看过 vLLM 的 Scheduler 源码吧？你觉得 vLLM v1 的调度器和你的 InfiniLM 调度器，最核心的理念差异是什么？

**候选人：** 我看的是本地 vllm 仓库 `vllm/v1/core/sched/scheduler.py`。它里面有一句很关键的注释：**vLLM v1 的 scheduler 里没有独立的 "decoding phase" 和 "prefill phase"，每个 request 只有 `num_computed_tokens` 和 `num_tokens_with_spec`**；每步 scheduler 只是分配 token，让 `num_computed_tokens` 去追 `num_tokens_with_spec`。
这个抽象比我做的“prefill / decode 显式两态”更通用：chunked prefill、prefix caching、投机解码、未来 jump decoding 都能用同一个机制表达。InfiniLM 当时是显式维护“这个请求 prefill 到第几个 token、decode 是否在跑”的状态机，思路一致，但抽象粒度没有 vLLM 那么统一。

**面试官：** vLLM 的 chunked prefill 具体是怎么用代码实现的？你对比自己实现，差距在哪？

**候选人：** vLLM 的做法是维护一个 `token_budget = max_num_scheduled_tokens`（默认等于 `max_num_batched_tokens`）。调度 waiting request 时：
```python
num_new_tokens = request.num_tokens - num_computed_tokens
if not enable_chunked_prefill and num_new_tokens > token_budget:
    break
num_new_tokens = min(num_new_tokens, token_budget)
```
也就是一个长 prefill 可以只先拿一部分 token 跑，跑完后 `request.num_computed_tokens += num_new_tokens`；如果它还没追平 `num_tokens`，下一步继续作为 running/prefill chunk 再调度，直到 prefill 完成。这种 token 级预算非常细。
我的 InfiniLM 也实现了 chunked prefill，但当时 KV cache 还是按整块分配的，不是完整 paged，所以 chunk 不能切得太小，否则 KV 块分配开销会吃掉收益。这是我和 vLLM 比最明显的差距：**vLLM 是 page 级 KV + token 级预算，我是“块级 KV + 较粗的 chunk”**。

**面试官：** vLLM 的抢占策略你了解吗？它和你做的请求状态保存/恢复是不是一回事？

**候选人：** 不完全是一回事。vLLM v1 `scheduler.py` 里，当 KV block 分配失败时会 preempt 一个 running 请求：`_preempt_request` 会 `kv_cache_manager.free(request)`，把 `num_computed_tokens` 清零，状态改成 `PREEMPTED`，再放回 waiting 队列。也就是说 vLLM v1 这条路径本质是 **recompute 式抢占**，后面重新从头 prefill，能复用前缀缓存的部分再复用。
我做的 InfiniLM 是“保存 token 级状态并恢复”，更接近一种轻量 checkpoint/resume：停下来时记住 prefill 到第几个 token、KV 在哪个块，之后从断点继续。这在思路和实现上比 vLLM v1 的“清 0 重算”更细，但代价是我要额外维护状态机；vLLM 是选择用更简单的 recompute + prefix cache 来换取调度器简单和鲁棒。两者各有取舍。

**面试官：** vLLM 的调度队列是怎么实现的？它只有 FCFS 吗？

**候选人：** vLLM v1 `request_queue.py` 里有 `SchedulingPolicy` 枚举，支持 `FCFS` 和 `PRIORITY` 两种。`FCFSRequestQueue` 就是 deque，先进先出；`PriorityRequestQueue` 是 heapq，按 `(priority, arrival_time)` 排序，priority 小、到达早的先调度。InfiniLM 当时基本只有 FCFS，所以遇到高并发长短混合会“长 prefill 堵车”，这也是我后来改成连续批处理 + chunked prefill 的动因之一。

**面试官：** 最后一个对比：vLLM 不是也支持 prefill/decode 混排吗？那你做的“混合 P/D”有什么独特价值？

**候选人：** 需要分两层说。vLLM v1 的 scheduler 因为不区分 prefill/decode 阶段，天然可以在一轮里同时调度 running 的 decode 和 waiting 的 prefill chunk；但模型 runner 和 attention 后端是否高效支持混排是另一回事，社区里很多人还是倾向 P/D 分离甚至 P/D disaggregation 来保 decode 延迟。
我的 InfiniLM 是在一个自研 C++ 框架里，针对纯文本模型明确做了“混合 P/D 批次 + 动态调 chunk”，并且实测没有把小 batch decode 延迟打爆。它不是新算法，而是在受限的框架里做了一版务实的策略：**decode 吃带宽、prefill 吃算力，两者资源画像互补就混；多模态视觉编码器不适合 chunk 就分开**。面试里我会强调这个权衡，不会说成比 vLLM 更先进。

**面试官：** 接着说 DeepSeek-V4 Mini 1B。这个模型和常见 LLM 比有什么特别之处？你的适配工作量花在哪了？

**候选人：** V4 Mini 1B 比较新的地方是"混合系数注意力"（CSA）这一族结构：里面包括压缩选块、HCA 重度压缩注意力、SWA 滑窗注意力；MoE 不用说了；还有 mHC 超连接这类连接结构。适配工作量主要在两层：
1. **权重映射**：HF checkpoint 的参数名和排布是按 PyTorch reference 约定的，框架内部有自己的参数组织和融合方式。CSA 里还夹带 KV 压缩矩阵这类特殊权重，对齐是单独的活；
2. **算子语义对齐**：CSA 的压缩/选块、HCA 的重度压缩，框架里没有现成算子，能拼的用已有算子拼，拼不出来的先用朴素实现顶上，先保证"语义对"，再谈性能。

**面试官：** 这种新架构模型适配，最怕的就是不知道"哪里错了"。你从 0.51 一路查到 0.077，具体用的是什么方法？应该不是一张图一张图看吧？

**候选人：** 对，我总结成一套可复用的方法：**参照系 + 分层二分 + 变量隔离 + 中间张量对齐**。
1. **先建参照系**：框架自带的 Python reference 不可用，我就用 checkpoint 自带的 `modeling_deepseek_v4.py` 当 ground truth，所有误差都跟它比；
2. **权重映射是地基**：checkpoint 去掉 77 个 MTP 键后剩 1812 个，和 C++ 模型 missing=0、unexpected=0，先保证每个参数都落在正确位置；
3. **逐层二分**：从 0 层模型开始，一层层往上加，看误差在哪一层跳变。结果 0 层一致、加第 1 层就跳，锁定问题在第 1 层；
4. **组件置零**：单层内把 attention 权重置零、FFN 置零分别跑，谁置零后误差消失问题就在谁。结果锁定 attention 路径；
5. **position 钉 0**：把 position_ids 全设成 0，RoPE 角度为 0、cos=1/sin=0，退化成恒等变换，误差从 0.27 掉到 0.025，argmax 恢复一致——问题锁死在 RoPE；
6. **算子直接对拍**：写一个 PyTorch split-half RoPE reference，和 C++ 的两种 RoPE 实现直接比，确认哪个布局对。

这套方法的好处是把一个"24 层黑盒"拆成单变量实验，每次只动一个变量，能给出可解释的证据链。

**面试官：** 那最后定位到的 5 处 RoPE 差异分别是什么？

**候选人：** 五处，全是稀疏注意力正确性的关键依赖：
1. **正向 RoPE 旋转布局**：C++ 用的 GPT-J 交错（0-1、2-3 配对），reference 是 GPT-NeoX split-half（i 与 i+half 配对）；
2. **fused SWA 内核的输出逆 RoPE 布局**：同样用了交错配对，改成 split-half，涉及 `swa_prefill / swa_decode / compressed_decode` 三个 CUDA 内核；
3. **压缩块 RoPE 位置**：原来用块首 `block*m`，reference 是块末 `block*m+(m-1)`——压缩块代表这段的摘要，因果上要等这段全出来才能被后面 query 看到；
4. **压缩块因果掩码 off-by-one**：`visible_blocks = (q_pos+1)/m` 改成了 `q_pos/m`，多算一个块会让后面的 query 提前看到不该看的压缩块；
5. **rope theta 路由**：原来的实现把压缩层所有 RoPE 都用了 `compress_rope_theta=160000`，实际上 q、滑动窗口 KV、输出逆 RoPE 都用主 `rope_theta=10000`，只有压缩 KV 用压缩 rope。

**面试官：** 那你凭什么判断剩下 0.077 是 BF16 精度累积，而不是还有隐藏 bug？

**候选人：** 核心证据是"单层全对齐、全模型才翻"。修完 5 处 RoPE 后，单独跑第 0 层（SWA）、第 2 层（CSA，ratio=4）、第 3 层（HCA，ratio=96），mean_abs 分别是 0.0236 / 0.0074 / 0.0081，首 token argmax 全部和 reference 一致。如果还有结构 bug，单层通常也会不一致；单层都一致说明算子语义和权重映射都对了。24 层累积到 0.077 后 argmax 可能会翻，这是 C++ 和 PyTorch 运算顺序、BF16 舍入不同导致的累积误差。要再往下做就是逐算子 BF16 舍入对齐，那是精度打磨，不是找逻辑错误。

**面试官：** logits 误差从 0.51 降到 0.077，这个误差怎么量的？0.077 算达标吗？

**候选人：** 度量方式是：同一输入，框架输出和 PyTorch reference 输出的 logits 误差（我们报告里用的是归一化后的误差指标）。0.51 → 0.077 的变化，主要功劳在权重映射改对——0.51 里面相当一部分是"参数放错位置 / scaling 没对齐"造成的系统性错误，不是浮点精度问题。

0.077 这个水平，配合"单层 argmax 与 reference 完全一致"，对推理框架来说算达标：采样主要看 logits 的相对大小和排序，0.077 不会改变最终分布走向。要较真还能再降，比如把 layer norm、RoPE 的浮点行为再对齐，但对服务可用性来说 0.077 已经够用。这是我们当时的明确取舍。

## 六、环节五：项目拷打（三）——NineToothed 算子开发与异构部署（42–48 min）

**面试官：** 第三个项目。NineToothed 是什么？跟 Triton 什么关系？你们为什么用它？

**候选人：** NineToothed 可以理解成一个类 Triton 的 Python DSL：用类似 Triton 的语法写 kernel，它负责 codegen 到不同后端。它跟 Triton 最大的差别是对国产 GPU 的覆盖——天数智芯、沐曦、摩尔线程都有后端，一套代码可以编译到多个平台。我们是算子仓库的 contributor，任务就是用它在这些异构卡上补齐 PyTorch 算子，并保证语义一致。

**面试官：** 你们写了 roll、column_stack、meshgrid、cartesian_prod、mode、frac 六个算子。挑一个最不 trivial 的说，比如 mode——GPU 上怎么做众数？

**候选人：** mode 在 GPU 上本质是"归约 + 计数"问题，坑在于数值范围不定，不能开固定大小直方图；并行计数又必然有竞争。我们当时的思路是"atomicAdd 直方图 + 归约找峰值"：先把输入分块，每个线程块在 shared memory 里用原子操作统计局部直方图，再归约找最大计数对应的值。有两个细节必须处理：
1. **tie-breaking**：多个值计数相同，PyTorch 的 mode 有确定的取法，要跟 reference 对齐；
2. **原子操作确定性**：不同 GPU 的 atomic 顺序不同，不能依赖顺序，我们要写确定性的 tie 逻辑。

roll 表面是 copy，难点在边界环绕和多维组合：沿某个维度滚 n 位，头尾要互换，朴素实现每个输出位置算一次取模，GPU 上整数模运算很慢；跨维度滚动时访存模式也会乱，如果 block/thread 映射设计不好，coalesced 就没了。

**面试官：** 异构卡上验证，你们遇到最典型的坑是什么？

**候选人：** 三类，按踩到频率排：
1. **数值类型支持不一致**：某家卡的编译器对 fp16 支持弱，或者精度路径有差异，我们只好在验证矩阵里做 dtype 覆盖；
2. **原子操作的行为差异**：int 原子累加谁支持、谁不支持、原子性保证到什么程度，各家不一样，不支持就得换等价写法；
3. **DSL 语法覆盖不全**：NineToothed 对某家后端可能不支持某个语法特性，得绕路。

所以我一直说，异构适配里"正确性验证体系"比"写 kernel 本身"更重要。我们做了三层：单算子对拍（多 shape、多 dtype 和 PyTorch reference 对比）、算子组合的端到端用例、集成测试。

**面试官：** 最后一个简历问题：你最早是 YOLO、RKNN 部署，为什么转到大模型推理？

**候选人：** 做端侧部署时我接触到量化、算子、runtime 这些底层，发现真正让我兴奋的是"怎么把模型跑得更快更省"，而不是调精度本身。大模型推理是同一个问题的放大版，而且当时 RKNN 量化也踩过坑：火焰这种小目标特征占比小，量化后漏检，后来靠 per-channel 校准和部分层混合精度解决。这些经验让我更确认要走推理系统方向，就集中转过来了。视觉训练和部署经验也不浪费，对多模态模型的感知是有帮助的。

## 七、环节六：技术八股快问快答（48–58 min）

**面试官：** 项目聊得差不多了，下面随便问点基础，紧张就说不会，没关系。

**Q1（量化粒度）：** per-tensor、per-channel、per-group 什么区别？为什么现在 LLM 量化事实标准是 per-group 128？

**候选人：** per-tensor 是整个张量共用一个 scale，最省、精度最差；per-channel 是每个输出通道一个 scale，精度最好但开销大；per-group 是折中——每 128 个相邻权重共享一个 scale，既控制 scale 数量，又保住精度。LLM 权重分布里 channel 内往往还有局部 outlier，per-group 128 能在简洁性和精度之间取得很好平衡，所以成了事实标准。

**Q2（prefill/decode 瓶颈）：** 为什么说 decode 是 memory-bound，prefill 是 compute-bound？你的判断依据是什么？

**候选人：** 看算术强度。decode 阶段每个 token 只算很少的矩阵向量乘，但每步都要把整个权重从显存读一遍，访存量远大于计算量，所以 memory-bound；prefill 阶段是一次性处理很多 token，矩阵乘的复用率高，单位数据能执行更多 FLOPs，通常更接近 compute-bound。可以用 Roofline 模型验证：把模型在目标 GPU 上的计算峰值和显存带宽画出来，看 kernel 的 arithmetic intensity 落在哪个区域。

**Q3（KV Cache）：** KV cache 为什么要缓存？它主要吃显存还是带宽？你能说说 paged attention 解决什么问题吗？

**候选人：** 自回归生成每步只计算当前 token，但 attention 需要和历史上所有 token 的 K/V 做运算，所以把历史 K/V 缓存下来避免重复计算。它既吃显存也吃带宽，长上下文场景下显存增长很快。paged attention 借鉴操作系统的分页思想，把 KV 按固定大小的 block 分配，避免为每个请求预留连续大块导致碎片和浪费，也让不同请求的 KV 块在物理上可以离散存放，从而支持更大的 batch 和更灵活调度。

**Q4（vLLM 调度）：** continuous batching 相比 static batching 的核心收益是什么？

**候选人：** static batching 通常等一批请求全部完成后才释放资源，短请求会被长请求拖死；continuous batching 是迭代级调度，一个请求完成就立刻腾出 slot 给新请求，GPU 空转少、尾延迟低、吞吐高。这也是在线推理服务普遍采用它的原因。

**Q5（并行策略）：** TP、PP、DP 各解决什么问题？什么时候通信会成为瓶颈？

**候选人：** DP 是数据并行，每张卡放完整模型、吃不同 batch，主要处理吞吐扩展，但单卡放不下时没用；TP 是张量并行，把每层参数切到多卡，能降低单卡显存，但每层都可能做 all-reduce，通信频繁，通常机内 NVLink 才能扛住；PP 是流水线并行，按层切分，通信量相对小但有 bubble，适合模型极大、跨机场景。通信成为瓶颈的典型信号：多卡扩展效率不随卡数线性增长，kernel 时间占比下降但通信时间占比上升，TP 维度过高 + 网络带宽不足就会很痛。

**Q6（FlashAttention）：** FlashAttention 的核心优化思想是什么？

**候选人：** 一句话：**不把完整的 N×N 注意力矩阵写到 HBM，而是在 SRAM 里分块计算并在线做 softmax 的 rescaling**。它把计算和访存重排，避免 O(N²) 的中间矩阵显存/带宽开销，同时利用分块提高 SRAM 复用率。所以它的加速主要来自减少 HBM 访问，而不是减少 FLOPs——实际 FLOPs 还略多。

**Q7（CUDA 基础）：** CUDA 里 coalesced memory access 是什么？为什么重要？

**候选人：** coalesced access 就是让一个 warp 里的 32 个线程访问的地址尽量连续，硬件可以把这些访问合并成少数几次内存事务。如果地址跳跃、错开，就会发多次事务，访存效率急剧下降。很多 kernel 慢不是因为算不快，而是访存模式不 coalesced。

**Q8（Profiling 方法论）：** 如果 GPU 利用率已经 100%，但业务吞吐还是不够，你会怎么继续优化？

**候选人：** 100% 利用率只说明 GPU 没闲着，不等于效率高。下一步我会分两层看：
1. 用 profiler 看 kernel 时间分布，是不是某个 kernel 占大头，然后用 Roofline 判断它是 compute-bound 还是 memory-bound；compute-bound 想减少指令/提高并行度，memory-bound 想减少访存/提高缓存命中；
2. 看调度层能不能少算——比如是否有多余的中间拷贝、没有融合的 elementwise、可以复用的 KV、可以投机生成的地方。利用率 100% 的时候，优化方向往往不是"把 GPU 填满"，而是"让 GPU 做更少无用功"。

**Q9（多卡扩展）：** 多卡扩展效率怎么测？如果 8 卡只比 1 卡快 4 倍，你会怎么分析？

**候选人：** 测法很简单：固定模型和 batch 总量（或按卡数线性增加 batch），测 1 卡、2 卡、4 卡、8 卡的 throughput，算 speedup 和每卡效率。8 卡只有 4 倍，我会先看是不是 batch 太小导致通信占比高；再看 TP/PP 配置是否合理；然后用 profiler 统计通信时间占比、看有没有 straggler（某卡明显更慢）；最后检查负载均衡，比如 MoE 里 expert 路由不均衡会导致某几张卡过载。

**Q10（数据加载）：** 训练/推理里数据加载慢，你会怎么定位和优化？

**候选人：** 先看数据加载是否成为 pipeline 的瓶颈：如果 GPU 利用率低、而 dataloader 的吞吐低于 GPU 消费速度，就是了。优化手段通常是几件套：多进程/多线程预取、pin memory + 异步 H2D 拷贝、减少解码/预处理开销、缓存预处理结果、调整 batch 和队列深度。定位工具上，PyTorch Profiler 能看 DataLoader 时间，Perfetto/perf 可以看 CPU 热点。

## 八、环节七：反问环节（58–60 min）

### 10.2 INT4 / INT8 / 算力 / 为什么能加速

**面试官：** 910B 支持 INT4 吗？INT4 和 INT8 区别是什么？为什么 INT8 可以做 INT4 的运算？

**候选人（复盘后理想回答）：** 这里要分“硬件原生算力”和“软件/算子支持”两层说：
- 910B 更常被明确支持的是 INT8，INT4 更多以 **W4A16 weight-only 量化**形式被框架支持：权重以 INT4 存储/传输，GEMM 前在算子内部做 anti-quant/dequant 到 FP16/BF16 再算，或者把两个 INT4 打包进一个 INT8/INT32 让 INT8 通路去处理。
- INT4 和 INT8 的区别：量化范围/精度不同，INT4 表示范围 `[-8,7]`，INT8 是 `[-128,127]`；同样存一个权重，INT4 只需要 INT8 一半的 bit，带宽和显存占用更低，但对 outlier 更敏感，所以一般要 per-group scale。
- 为什么 INT8 能做 INT4 的运算：因为一个 8-bit container 可以装两个 4-bit 数值。只要算子在加载/解包时做好符号扩展和 dequant，INT8 的乘加单元可以处理 INT4 数据；很多 NPU 的 GEMM 也通过 anti-quant scale/offset 在算子内把 INT4 还原成高精度参与矩阵乘。

**面试官：** INT8 和 INT4 的算力是多少 TOPS？

**候选人（现场没答好）：** 这个数字我当时没背，直接说不知道了。复盘后应该补：
- 昇腾 910B 常见规格是 **FP16 约 376 TFLOPS、INT8 约 752 TOPS**（不同型号/降频配置有差异）；
- INT4 不一定有官方标准 TOPS，很多场景是“存储减半 + 访存减半 + 算子内反量化”，不能简单认为 INT4 算力是 INT8 的 2 倍；
- 面试里如果真不确定，可以说“具体卡型规格我记不精确，但我知道查 `npu-smi`/官方 Atlas 规格表；INT4 的收益更多来自 memory-bound 场景的带宽和显存，而不是峰值计算。”

**面试官：** INT4 为什么可以加速？

**候选人：** 大模型 decode 是典型的 memory-bound：每个 token 要读一遍全部权重，权重从 FP16 变 INT4 后，**需要从 HBM 读的字节数降到 1/4**（相对 FP16）或 1/2（相对 INT8）。这直接降低访存时间、提高 cache 命中，也能让同样显存装下更大 batch，从而提升吞吐。如果算子本身没有原生 INT4 算力，收益主要来自存储/带宽而不是 FLOPs 提升。

### 10.3 Qwen3 架构拷打：qkv / FFN / 精度

**面试官：** Qwen3 的 attention 从 qkv 开始讲，维度是多少？精度是多少？

**候选人（复盘后理想回答）：** 以 Qwen3-8B 为例：
- hidden size = **4096**；
- num_attention_heads = **32**，head_dim = **128**；
- GQA：num_key_value_heads = **8**；
- 所以 `q_proj` 输出是 **4096**，`k_proj` / `v_proj` 输出各是 **1024**；
- vLLM 里 fused 的 `qkv_proj` 维度就是 `q + k + v = 4096 + 1024 + 1024 = 6144`；
- 精度：Qwen3 模型权重/激活通常用 **BF16**。在 W4A16 里，4 是 weight 位宽，16 表示激活/计算精度是 16-bit；这里 Qwen3 用的是 **BF16**，不是 FP16。

**面试官：** FFN 的 gate、up、down 维度？

**候选人：** Qwen3-8B 的 `intermediate_size = 14336`：
- `gate_proj`：`[14336, 4096]`
- `up_proj`：`[14336, 4096]`
- `down_proj`：`[4096, 14336]`

Qwen3-30B-A3B 这种 MoE 不一样：hidden=2048，`moe_intermediate_size=768`，gate/up/down 都是逐 expert 的小矩阵。

**面试官：** W4A16 里的 16 是 fp 还是 bf？Qwen 里用的是哪个？

**候选人：** 16 指的是 activation/compute path 的 16-bit 精度，具体可以是 FP16 或 BF16，取决于模型。Qwen3 官方通常是 **BF16**，所以 vllm-ascend 里加载 Qwen3 时 `dtype="bfloat16"`，`qscales`/`awq_scale` 也存成 bf16。

### 10.4 per-channel / per-group / per-token / per-tensor 量化

**面试官：** per-channel、per-group 区别？再补一个 per-token/per-tensor。

**候选人（复盘后理想回答）：**
- **per-tensor**：整个权重/激活张量共用一个 scale，最简单最省，但对分布不均的大模型精度差；
- **per-channel**：每个输出通道一个 scale，能更好保护不同通道的数值范围，开销比 per-tensor 大；
- **per-group**：每连续 128 个权重共享一个 scale，是 per-channel 和 per-tensor 的折中；LLM 权重常有局部 outlier，group 量化能在不引入太多 scale 的情况下保住精度；
- **per-token** 一般用于激活/动态量化：每个 token 的行单独一个 scale，因为不同 token 的激活幅度差异可能很大；在 W8A8 动态量化里常见 per-token activation scale + per-channel weight scale。不要和 per-channel 权重量化混在一起讲。

### 10.5 EPLB（专家并行负载均衡）

**面试官：** 是否了解 EPLB？核心机制是什么？

**候选人（现场没怎么学，复盘后补强）：** EPLB 是 Expert Parallelism Load Balancing，解决 MoE 在专家并行下“热门专家被分到某张卡、导致负载不均”的问题。核心思想不是静态把 expert 平均分到各卡，而是：
- 动态统计每个 physical device 上的 expert token 数/负载；
- 维护 logical expert → physical expert 的映射 `log2phy`，甚至对热门专家做冗余副本；
- dispatch 阶段根据映射把 token 路由到负载更低的 physical expert，combine 阶段再把结果按原始路由权重合并回来。
在 vllm-ascend 里可以看到 `dynamic_eplb`、`expert_map`、`log2phy`、`expert_tokens` 这些机制，都是为了支持运行时动态负载均衡。

### 10.6 DeepSeek-V4 拷打

**面试官：** 你做的是 Mini 模型？怎么不用完整版？

**候选人（现场被吐槽，复盘后修正）：** 对，做的是 DeepSeek-V4 Mini 1B。原因很直接：完整 V4-Flash 是 284B MoE / 13B 激活，单张 24GB 4090 根本放不下；Mini 1B 是同架构缩小版，2GB 左右，单卡能跑，适合验证“权重映射 + CSA/HCA/MoE/mHC 算子语义 + 数值对齐”这套适配正确性。方法验证完后，完整版可以复用同样的适配逻辑，只是需要多卡和更大显存。

**面试官：** 这种量化/剪枝模型的上下文长度是多少？

**候选人（复盘后答案）：** 完整 DeepSeek-V4-Flash 的官方定位是 **1M context**。Mini 1B 是同一架构的缩小版，具体 `max_position_embeddings` 要查模型 `config.json`；我当时没有背这个数字。面试里最好回答“V4 系列主打百万级长上下文，但我适配时主要验证的是单层/短序列数值正确性，没有压满上下文长度”。

**面试官：** 讲一下 CSA、HCA。indexer 的目的是什么？top-k 是多少？V4-Flash 的 k 值是多少？

**候选人（复盘后理想回答）：**
- **CSA（Compressed Sparse Attention）**：把历史 KV 先压缩成 block，再用一个轻量 **Lightning Indexer** 从可见压缩块里选 top-k 个相关 block，和滑动窗口一起做 attention；
- **HCA（Heavily Compressed Attention）**：也把历史压缩成 block，但**不用 indexer 选块**，而是对全部压缩块做重度压缩后整体 attention；
- **Indexer 的目的**：用很小的 query/key 去预测“哪些历史压缩块对当前 token 重要”，只注意 top-k 个 block，避免 attention 随序列长度线性膨胀；
- **top-k 值**：代码里是配置项 `config.index_topk`，具体数值应该以官方 `config.json` 为准。我本地看到的是通过 `self.config.index_topk` 传给 `LightningIndexer.select(...)`；如果面试官追问 V4-Flash 的具体 k，我印象中 CSA 的 indexer 会选比较少的压缩块（常见 `index_topk=4` 这类值），但我不应该现场硬编，最好说“我确认过 config 再给准确值”。
