## 二、赛题理解

根据当前拿到的题面信息，本题聚焦 `InfiniLM` 推理服务在多并发、长文本场景下的服务能力优化，测试模型包括：

- 8B 模型
- 70B 模型

当前理解的核心目标为：

- 在多并发请求场景下提升输出吞吐与总吞吐量；
- 在长输入、长输出请求场景下保持较好的服务稳定性；
- 在小规模测试场景中不出现明显性能下降，如有提升可作为加分项；
- 最终以可运行的推理服务、可复现的压测脚本和性能结果分析作为主要交付内容。

从题目性质来看，这不是单纯的模型适配任务，而是典型的推理系统优化问题。优化重点落在请求调度、批处理策略、KV Cache 管理、长序列路径、Attention 后端与图执行开关等系统层机制，而不是模型结构本身。

## 四、当前仓库与服务链路理解

### 1. 仓库定位

根据 `InfiniLM` 公共仓库 README，`InfiniLM` 是一个基于 `InfiniCore` 的推理引擎，支持多种设备后端，并提供：

- 单次推理入口；
- 分布式推理入口；
- OpenAI 兼容风格的推理服务接口；
- 服务性能测试脚本；
- 模型基准测试入口。

### 2. 服务入口理解

当前题目给出的服务入口为：

```bash
python python/infinilm/server/inference_server.py \
  --device nvidia \
  --model=/<path-to>/9g_8b_thinking_llama/ \
  --temperature 1.0 \
  --top-p 0.8 \
  --top-k 1 \
  --port 8102 \
  --tp 1 \
  --max-new-tokens 4096 \
  --num-blocks 6144 \
  --max-batch-size <max_con> \
  --enable-graph \
  --enable-paged-attn \
  --attn flash-attn \
  --ignore-eos
```

结合 `InfiniLM` 仓库中的 README 与 `python/infinilm/server/inference_server.py`，当前已确认该服务具备以下特征：

- 提供 OpenAI 兼容风格的 `/v1/chat/completions` 接口；
- 支持流式输出；
- 支持按配置切换 `paged` 或 `static` cache；
- 支持 `flash-attn` 等 attention 后端；
- 支持 `enable_graph` 图执行开关；
- 支持 `max_batch_size`、`num_blocks`、`max_new_tokens` 等关键服务参数。

从这些接口可以看出，比赛题目的优化空间主要集中在推理服务运行时参数与服务内部调度策略上。

### 3. 压测方式理解

当前题面给出的参考压测脚本，核心上是通过 `vllm bench serve` 对 OpenAI 兼容服务接口发起压力测试，并对不同组合进行遍历：

- `max-concurrency` / `batch_size`
- `random-input-len`
- `random-output-len`

从脚本结构看，当前压测方式重点关注：

- 爆发式请求输入；
- 不同输入长度对 prefill 阶段的影响；
- 不同输出长度对 decode 阶段的影响；
- 并发度变化对整体吞吐与服务稳定性的影响。

### 2. 预研中已确认的关键参数

结合题面命令与仓库服务入口，当前已确认与服务能力优化强相关的参数包括：

- `--max-batch-size`
- `--max-new-tokens`
- `--num-blocks`
- `--tp`
- `--enable-graph`
- `--enable-paged-attn`
- `--attn flash-attn`
- `--ignore-eos`

这些参数分别关联到：

- 最大并发承载能力；
- 输出长度上界；
- KV Cache 资源配置；
- 张量并行规模；
- 图执行优化；
- 分页注意力缓存策略；
- Attention 后端性能；
- 生成终止逻辑。

### 3. 当前已形成的工程认识

基于当前预研，已经形成以下初步认识：

- 本题首先要做的是稳定复现基线服务与基线压测流程；
- 8B 与 70B 的优化重点可能不完全一致；
- 长文本场景下，`prefill` 与 `decode` 两个阶段的瓶颈需要分开看；
- 多并发场景下，仅调高 `max_batch_size` 不一定直接带来吞吐提升，还需要结合 KV Cache、Attention 后端和调度行为综合判断；
- 小规模场景“不明显下降”意味着优化方案不能只面向大并发极限压榨，还需要兼顾低并发和中等长度请求。

## 六、阶段性技术分析与拟优化方向

当前阶段尚未形成正式性能结果，因此本节主要记录基于仓库结构、服务命令和题目目标所做的技术预判，不将其写成既成优化成果。

### 1. 批处理与并发承载能力

本题的直接目标之一是提升多并发场景下的总吞吐，因此批处理能力是优先级最高的方向之一。当前预判可重点关注：

- 服务内部是否能稳定把同时到达的请求聚合成有效 batch；
- `max_batch_size` 配置变化后，吞吐提升是否被其他环节限制；
- 长输出请求是否会造成 batch 长时间占用，影响后续请求进入。

这一方向通常直接影响：

- 吞吐上限；
- 队列等待时间；
- 大并发下的资源利用率。

### 2. 长文本场景下的 KV Cache 管理

题目明确覆盖长文本服务场景，而当前服务命令中已经显式使用：

- `--enable-paged-attn`
- `--num-blocks`

因此可以判断，KV Cache 的分配与管理很可能是长文本场景表现的重要因素。当前拟重点关注：

- `num_blocks` 配置与最大并发、最大输出长度之间的平衡；
- 长上下文下缓存块的占用和回收行为；
- `paged attention` 对显存利用率与吞吐的影响。

### 3. Attention 后端选择

题面参考命令中使用了：

- `--attn flash-attn`

这说明当前服务路径已经具备可替换的 attention 后端。后续需要重点验证：

- `flash-attn` 在目标模型和目标 batch 场景下是否始终占优；
- 对长输入、长输出场景，attention 后端差异是否会放大；
- 不同后端对小规模请求性能是否存在回退。

### 4. CUDA Graph 与稳定 decode 路径

题面参考命令中启用了：

- `--enable-graph`

从服务优化角度看，CUDA Graph 更可能在稳定形状或相对稳定执行路径下带来收益，因此后续值得观察：

- 长输出 decode 场景中，图执行是否可以降低调度与 launch 开销；
- 不同 batch 形态下，图执行的收益是否稳定；
- 图执行是否会带来额外的初始化、内存或兼容性问题。

### 5. 8B 与 70B 两类模型的差异

当前题面同时包含 8B 和 70B 模型，因此优化策略不能简单假设完全通用。当前阶段的理解是：

- 8B 更适合先快速建立基线和验证方向；
- 70B 更可能暴露多卡、KV Cache、显存占用、长序列服务等更复杂的问题；
- 两者在最优 `max_batch_size`、`tp` 规模与长输出承载能力上可能存在明显差异。

因此后续更合理的方式是：

- 先在 8B 上完成服务与压测路径闭环；
- 再迁移到 70B，做更接近正式评测环境的验证。

## 七、当前问题与风险

当前阶段主要问题如下：

- 还没有形成正式的基线性能数据，当前无法给出吞吐提升幅度；
- 题面的完整测试矩阵暂时无法在当前材料中完整展示；
- 8B 与 70B 的真实瓶颈位置可能不同，需要实际压测后才能进一步确认；
- 服务能力优化通常受多因素共同影响，仅靠单参数调整很难保证整体最优；
- 小规模场景要求“不明显下降”，意味着优化方案必须兼顾不同负载区间。

此外，当前还需特别注意两点：

- 如果过早在没有基线数据的前提下进行复杂改动，后续很难判断收益来源；
- 如果只关注大并发极限吞吐，而忽略小并发和中等长度请求表现，可能不符合题目整体要求。

## 八、后续计划

下一阶段计划按以下顺序推进：

1. 跑通 8B 模型的基线服务与基线压测流程。
2. 记录不同 `max-concurrency / input-len / output-len` 组合下的基础表现。
3. 结合实际日志与表现，初步区分 prefill 和 decode 阶段的主要瓶颈。
4. 围绕 `max-batch-size`、`num-blocks`、`paged attention`、`flash-attn`、`enable-graph` 做第一轮参数级优化实验。
5. 在参数优化基础上，再判断是否需要进入服务内部调度或缓存管理层面的代码改动。
6. 在 8B 路线形成较稳定方案后，迁移到 70B 模型进行验证。
7. 最终形成性能对比、优化说明、代码修改和测试报告。

也可以进一步拆成 4 个阶段：
