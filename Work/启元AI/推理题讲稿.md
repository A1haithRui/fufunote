## 1）项目背景：先讲比赛和任务

这个项目是我参加 **InfiniLM 推理框架赛道** 时做的，而是 **优化推理服务能力**。  
场景上主要关注两类比较典型的问题：

- **高并发场景**：服务能不能稳住，吞吐能不能拉起来
- **长文本场景**：长 prompt 会不会拖慢系统，甚至引发 OOM

官方给了 InfiniLM 的整体框架和服务启动方式，我做的是在这个官方框架上做优化。  
服务端实际是通过 InfiniLM 的 `inference_server.py` 启起来的，  
而 `vllm bench serve` 在这里主要是作为 **压测工具/客户端**，不是用 vLLM 去替代 InfiniLM 服务端。用于执行推理任务并测指标。

所以这个项目本质上可以理解为：

> **基于官方 InfiniLM 服务框架，分析其调度瓶颈，并做工程优化。**

## 2）先讲评测设计：我是怎么发现问题的

为了先定位瓶颈，我没有直接上来改代码，而是先做了一套系统压测矩阵。  
测试对象是 **RTX 4090 单卡上的 Llama-3.1-8B-Instruct 服务**。

测试维度主要有三组：

- **并发数（con）**：1 / 4 / 16 / 64
- **输入长度（input）**：32 / 256 / 4096
- **输出长度（output）**：256 / 1024 / 4096

我主要关注以下几个服务指标：

- **TTFT**：首 token 延迟
- **TPOT**：每个输出 token 的平均生成时间
- **ITL**：相邻 token 之间的输出间隔
- **输出吞吐**：每秒生成多少输出 token
- **总吞吐**：输入输出 token 加总后的整体处理能力

这一步的目的其实很明确，不是单纯跑分，而是想回答两个问题：

1. **系统在哪些场景下会不稳定甚至出故障？**
2. **系统的服务瓶颈更偏向长输入问题，还是更偏向调度问题？**

---

## 3）再讲测试结论：两个异常点

测试下来，我重点关注到两个异常点：

### 异常点1：con=4，input=4096，output=1024

这个场景并发不算高，但输入很长。  
它暴露出来的核心问题是：

- Prefill 一次性要处理完整长 prompt
- 这会带来比较高的显存压力
- 容易触发稳定性问题，严重时会 OOM

也就是说，这个异常点更偏向 **长输入场景的显存与调度耦合问题**。

---

### 异常点2：con=16，input=256，output=256

这个场景输入其实不算特别长，但是并发升上来之后，  
我观察到服务能力并没有随着并发提升而合理放大，反而会出现明显的效率问题。

它更偏向暴露：

- Decode 阶段没有被优先保障
- 请求一多，系统调度容易让 Prefill 持续插队
- 导致已有请求的流式生成体验变差
- 进而影响 TPOT、ITL 和吞吐

也就是说，这个异常点更多反映的是 **高并发下的调度策略问题**。

## 4）然后讲：我回到原始 scheduler 里看代码，发现了根因

接下来我就回到 InfiniLM 原始调度器里看 `schedule()` 的实现。  
我发现它的调度逻辑非常关键的一点是：

> **它是 prefill-first，而且 Prefill 和 Decode 是分阶段、互斥执行的。**

具体来说，代码流程大概是这样：

1. 先处理 `waiting_queue`，也就是等待进入 Prefill 的请求
2. 只要这一轮成功从 waiting queue 里调度到了请求，就直接返回 Prefill batch
3. 这一轮就不会再继续处理 `running_queue` 里的 Decode 请求
4. 只有当 waiting queue 没有可调度请求时，才会去处理 running queue

这意味着它不是那种更理想的 **mixed batching**，而是：

- **有 Prefill 就先做 Prefill**
- **没有 Prefill 了才去做 Decode**

这个逻辑在普通场景下能工作，但在 **高并发和长输入** 下会有明显问题。

---

## 5）接着自然引出：三个缺陷

我把这个问题归纳成三个缺陷，正好也对应你 PPT 下面的三条。

---

### 缺陷1：P/D 共用一个全局 `max_batch_size`

Prefill 和 Decode 的资源特征其实完全不同：

- **Prefill** 更吃的是 **batch token 数**，因为它要一次性处理整段 prompt，激活峰值高
- **Decode** 更看重的是 **batch request 数 / sequence 数**，因为它每步通常只生成一个 token，更需要并行度

但原始框架里是用 **一个全局 `max_batch_size`** 去同时约束两个阶段。  
这就会导致一个很典型的问题：

- 如果把 batch size 调大，Prefill 容易失控，长输入下显存峰值顶不住
- 如果把 batch size 调小，Decode 的并行度又不够，吞吐上不来

所以这是一个非常典型的 **“一个参数同时控制两个性质不同阶段，结果顾此失彼”** 的问题。

---

### 缺陷2：Prefill 绝对优先，而且没有长输入隔离

原始调度器每轮都是先看 `waiting_queue`，只要有 Prefill 能调度，就先返回 Prefill。  
这样一来，新请求不断进来时，Decode 就容易被拖住。

尤其是当 waiting queue 里混入长输入请求时，问题会更明显：

- 长 prompt 的 Prefill 本来就重
- 又因为它优先级更高
- 所以会直接挤压 running queue 里的 Decode 请求

带来的后果就是：

- ITL 变差，流式输出变卡
- TPOT 拉长
- 输出吞吐下降

所以第二个问题本质上是：

> **Prefill 优先级过高，且缺少对长输入请求的隔离和保护。**

---

### 缺陷3：显存建模更偏 KV block，没充分约束 Prefill 激活峰值

从实现角度看，原始框架在接收请求和分配资源时，很大程度上是围绕 **KV cache block** 来做管理的。  
这套逻辑对于 Decode 很重要，因为 Decode 每一步都在申请和扩展 KV。

但问题是：

- **长输入 Prefill 的风险，不只来自 KV cache**
- 更大的压力其实还来自 **forward 过程中的激活峰值**

如果只从 KV block 角度去估资源，而没有充分约束 Prefill 阶段的激活峰值，那么：

- 看起来 KV 还能放得下
- 但实际 forward 一跑，还是可能 OOM

所以第三个缺陷本质是：

> **资源控制没有把 Prefill 的实际 forward 峰值压力管住。**

## 7）最后讲改进方案：三项工程优化

### 优化1：拆分独立的 P/D batch cap

既然 Prefill 和 Decode 的资源特征不同，  
那就不应该继续共用一个 `max_batch_size`。

所以我做的第一件事是：

> **给 Prefill 和 Decode 分别设置独立的 batch cap。**

这样可以做到：

- Prefill 单独限流，避免长输入时一次性把显存顶满
- Decode 单独保留并行空间，避免吞吐被拖垮

它解决的主要就是第一个缺陷。

---

### 优化2：引入 decode-first 调度策略

第二个优化是调度优先级调整。  
针对原来 “Prefill 绝对优先” 的问题，我引入了 **decode-first** 思路。

也就是说，在调度时优先保证 running queue 里的 Decode 请求，  
先保障已经在生成中的请求继续平稳输出，再处理 waiting queue 里的 Prefill。

这样做的核心收益是：

- 优先保障流式输出连续性
- 改善 ITL 和 TPOT
- 避免新来的 Prefill 长时间阻塞已有 Decode

它主要对应解决第二个缺陷。

---

### 优化3：加入长输入保护

第三个优化是 **长输入保护机制**。  
因为长 prompt 是最容易把 Prefill 峰值顶高的，所以我对长输入请求做了额外约束和隔离思路。

简单理解就是：

- 遇到长输入时，不让它无约束地和其他请求一起冲击 Prefill
- 让它在调度上受到更严格的保护和限制

这样做的目的是：

- 降低长输入导致的 Prefill 峰值风险
- 缓解 OOM
- 提升长文本场景下的稳定性

这项优化主要对应第二、第三个缺陷。

---

## 8）最后收束到结果

做完这几项优化后，我重新回到压测矩阵中验证。  
结果是：

- 在指定高并发场景下，**输出吞吐从 407.3 tokens/s 提升到 726.0 tokens/s**
- 提升幅度大约是 **78%**
- 同时也完成了 **长输入场景下的稳定性验证**

所以这个项目我最终想表达的核心不是“我改了几个参数”，而是：

> **我先通过压测矩阵定位异常，再回到原始调度器代码中抽象出三个结构性缺陷，最后用三项工程优化有针对性地改善了高并发和长文本场景下的服务能力。**
