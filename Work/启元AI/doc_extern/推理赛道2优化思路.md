# 推理赛道2服务能力优化思路

记录时间：2026-07-11

当前背景：
- 赛题：启元实验室推理服务能力优化，推理赛道 2-1-2。
- 当前模型：Llama-3.1-8B-Instruct。
- 当前远端平台：RTX 4090 24GB。
- 当前服务端：InfiniLM commit `7c1efb5`。
- 当前 baseline：远端 tmux 会话 `infini_server` 和 `infini_bench` 正在运行。
- 当前服务参数核心：`--enable-graph --enable-paged-attn --attn flash-attn --num-blocks 64 --max-batch-size 64 --ignore-eos`。

## 一、优化目标怎么判断

这道题不是单点低延迟题，目标是多并发、长文本服务场景下的输出吞吐和总吞吐提升，同时小规模性能不能明显下降。

建议所有优化都按这几类场景拆开看：

- 短输入长输出：`input=32, output=1024/4096`，主要看 decode 吞吐。
- 中输入长输出：`input=256, output=1024/4096`，兼顾 prefill 和 decode。
- 长输入：`input=4096`，主要暴露 prefill、KV cache 容量和调度问题。
- 高并发：`concurrency=16/64`，主要暴露 batch 调度、KV block 预留和 CPU 请求处理开销。

核心记录指标：

- `Successful requests`
- `Output token throughput`
- `Total Token throughput`
- `Mean/P99 TTFT`
- `Mean/P99 TPOT`
- `Mean/P99 ITL`
- 是否出现 timeout、OOM、`No available cache blocks`、服务 unhealthy。

## 二、第一阶段：先做参数扫描

这部分不改代码，风险最低，也最适合当前环境比较脆弱的情况。

### 1. `max-batch-size`

之前启动命令里出现过重复参数：

```bash
--max-batch-size 64 ... --max-batch-size 4
```

后面的 `4` 很可能覆盖前面的 `64`，导致高并发 baseline 偏低。当前已经改成只保留：

```bash
--max-batch-size 64
```

建议之后对比：

```text
max-batch-size = 4, 16, 64
```

重点看：

- `con=1/4` 是否下降。
- `con=16/64` 吞吐是否提升。
- 高并发 TTFT 是否明显变差。

### 2. `num-blocks`

当前：

```bash
--num-blocks 64
--block-size 256
```

总 KV token slot 约为：

```text
64 * 256 = 16384
```

这对 `con=64, output=4096` 理论上不够，因为调度器会为运行中请求的剩余输出预留 block。官方参考 `num-blocks=6144`，但 4090 24GB 大概率放不下。

建议逐步扫描：

```text
num-blocks = 64, 96, 128, 192, 256
```

先找“能启动、不卡死、不 OOM、高并发不失败”的最大值。

### 3. `block-size`

当前默认：

```bash
--block-size 256
```

大 block 的优点是 block table 短，元数据少；缺点是短输入和高并发时内部碎片大。官方矩阵里有大量 `input=32` 和 `output=256`，高并发下碎片可能明显。

建议对比：

```text
block-size = 128, 256
```

可能收益：

- `con=16/64, input=32/256` 更容易容纳更多请求。
- KV block 预留更细，减少因为单个请求预留过粗导致的等待。

风险：

- block table 变长。
- paged attention 元数据开销增加。
- 底层 kernel 可能对 256 更友好。

### 4. `INFINILM_MAX_NUM_BATCHED_TOKENS`

代码位置：

```text
python/infinilm/llm/llm.py
```

调度器会读取：

```python
max_num_batched_tokens = int(
    os.getenv("INFINILM_MAX_NUM_BATCHED_TOKENS", max_position_embeddings)
)
```

这个值限制一次 prefill schedule 能合批多少 token。

建议扫描：

```text
INFINILM_MAX_NUM_BATCHED_TOKENS = 1024, 2048, 4096, 8192
```

重点看：

- `input=4096` 的 TTFT 和总吞吐是否改善。
- 短输入高并发是否被长 prefill 阻塞。

### 参数扫描小矩阵

正式 30 点太慢，建议每组参数先跑小矩阵：

```text
con=1,  in=32,   out=256
con=4,  in=256,  out=256
con=16, in=256,  out=256
con=64, in=256,  out=256
con=4,  in=4096, out=256
```

小矩阵稳定后，再跑官方完整 30 点。

## 三、第二阶段：调度器优化

代码重点：

```text
python/infinilm/llm/scheduler.py
```

当前调度逻辑大致是：

1. 先处理 waiting queue 的 prefill。
2. 只要有 prefill batch，就直接返回。
3. 没有 prefill 时，才处理 running queue 的 decode。

这意味着长输入请求的 prefill 可能打断 decode，导致长输出、多并发时 TPOT 和 ITL 抖动。

### 可尝试策略：decode 优先或 prefill budget

思路一：running queue 非空时优先 decode。

思路二：限制每轮 prefill token 数，避免 `input=4096` 的长请求一次占用太久。

预期收益：

- `con=16/64, output=1024/4096` 的 TPOT 更稳。
- 输出吞吐可能提升。

风险：

- 新请求 TTFT 可能上升。
- 长输入 prefill 总耗时可能变长。

建议只做实验开关，不改默认行为，例如：

```bash
export INFINILM_SCHED_DECODE_FIRST=1
export INFINILM_PREFILL_TOKEN_BUDGET=2048
```

## 四、第三阶段：KV block 预留策略

代码重点：

```text
Scheduler.can_accept_request()
```

当前逻辑会为 running requests 的所有剩余输出 token 预留 block：

```python
remaining_tokens = req.sampling_params.max_tokens - req.get_num_generated_tokens()
num_blocks_needed = (remaining_tokens + self.block_size - 1) // self.block_size
```

这非常保守。比如 `output=4096` 时，每个请求会提前预留约 16 个 block。`con=64` 时需要非常多 block，即使 decode 实际是一 token 一 token 推进。

可实验：

- 每个 running request 只预留 1 到 2 个未来 block。
- 增加环境变量控制，例如 `INFINILM_DECODE_BLOCK_RESERVE=2`。

预期收益：

- 高并发更容易接收请求。
- waiting queue 不会因为过度预留而停住。

风险：

- 如果预留过少，decode 中途可能触发 `No available cache blocks`。
- 这是中风险改动，需要小矩阵验证。

## 五、第四阶段：服务端 CPU 路径

代码重点：

```text
python/infinilm/server/inference_server.py
python/infinilm/llm/llm.py
```

当前非流式 `_chat()` 仍然通过 `stream_request()` 收 token。`LLMEngine._update_requests()` 每个 token 都会做增量 `tokenizer.decode()`。

如果后面高并发时 GPU 利用率不满，CPU 侧 JSON、队列、文本 decode 可能成为瓶颈。

可做 benchmark 专用 fast path：

- 不逐 token decode 文本。
- 只累计 token id。
- 请求结束时一次性 decode，或者返回占位文本。

风险：

- OpenAI API 兼容性可能受影响。
- 只能作为显式实验开关，默认关闭。

建议开关：

```bash
export INFINILM_BENCH_FAST_TEXT=1
```

## 六、投机解码

代码里已有 draft model 相关入口：

```bash
--draft-model
--num-draft-tokens
```

如果能找到合适 draft model，长输出吞吐可能明显提升。

但当前环境脆弱，比赛时间紧，投机解码优先级不如参数扫描和调度器改动。建议作为后备大招。

## 七、推荐执行顺序

第一步：不改代码，扫参数。

```text
num-blocks: 64, 96, 128, 192
block-size: 128, 256
INFINILM_MAX_NUM_BATCHED_TOKENS: 2048, 4096, 8192
```

第二步：做调度器开关。

```text
decode-first
prefill-token-budget
```

第三步：做 KV block reserve 策略。

第四步：看 GPU 利用率，如果高并发时 GPU 不满，再优化 CPU/JSON/文本 decode 路径。

如果时间只够做一个代码改动，优先做调度器 decode 优先或 prefill budget。

如果时间只够做实验不改代码，优先扫 `num-blocks + block-size + token budget`。

## 八、当前接管后的实施方案

当前目标先从“跑出完整 baseline”转为“在不破坏环境的前提下，让官方矩阵可完成并找出可优化空间”。

### 阶段 1：保完成率

已经实施：

```text
在 scheduler.py 中增加 long-context batch cap。
在 running queue 非空时启用 decode-first，避免长 prefill 与长 decode 同时压到显存临界点。
```

当前验证：

```text
con=4, input=4096, output=1024, num_prompts=12 已完成，服务 healthy。
con=4, input=4096, output=1024, num_prompts=40 正在跑官方规模验证。
```

这一阶段接受的代价：

```text
TTFT 会很高。
长上下文请求近似串行执行。
但 benchmark 能完成，比服务 unhealthy 更重要。
```

### 阶段 2：收窄保护条件

当前 long-context 判定较保守：

```text
prompt_len >= 4096
或 total_len >= 4096
或 prompt_len + max_tokens >= 4096
```

这会把 `input=32/256, output=4096` 也纳入串行保护。baseline 已经证明这些短/中输入长输出点原本可以完成，因此下一步建议改成更窄的保护：

```text
只对 prompt_len >= 4096 的长输入请求强保护。
短/中输入 + 长输出仍走正常并发 decode。
```

预期：

```text
保住 input=4096 卡点的稳定性。
恢复 output=4096 短/中输入场景的并发吞吐。
```

2026-07-11 实施结果：

```text
已将默认 long-context 判定收窄为 prompt_len >= 4096。
新增 INFINILM_LONG_CONTEXT_USE_TOTAL_LEN=1 可恢复总长度判定。
decode-first 也已收窄为只延后 long-context 请求的 prefill，不再全局阻塞短输入请求。
```

验证结论：

```text
con=4,input=32,output=4096,num_prompts=8:
  output throughput = 137.01 tok/s，服务 healthy。

con=4,input=4096,output=1024,num_prompts=8:
  output throughput = 54.35 tok/s，服务 healthy。
```

当前推荐默认运行策略：

```bash
export INFINILM_LONG_CONTEXT_THRESHOLD=4096
export INFINILM_LONG_CONTEXT_MAX_BATCH=1
unset INFINILM_LONG_CONTEXT_USE_TOTAL_LEN
export INFINILM_DECODE_FIRST_WHEN_RUNNING=1
```

判断：

```text
这是目前最稳的比赛运行策略：只保护真正长输入，尽量不伤短/中输入长输出。
下一步优化重点应转向降低长输入 TTFT，以及验证 con=16/64 下是否会出现 KV block 不足。
```

### 阶段 3：探索高并发能力

在阶段 2 稳定后，再跑小矩阵：

```text
con=4,  input=4096, output=1024
con=4,  input=4096, output=4096
con=16, input=256,  output=256
con=16, input=256,  output=1024
con=64, input=256,  output=256
```

如果高并发出现 `Insufficient KV cache blocks` 但不是 CUDA OOM，再尝试 KV 预留策略：

```text
INFINILM_DECODE_BLOCK_RESERVE=1/2/4
```

如果高并发 GPU 利用率低，再考虑服务端 fast text/JSON 路径。

### 阶段 4：最终提交策略

最终代码应保留环境变量开关，不把实验策略写死：

```text
默认行为尽量接近原始实现。
比赛运行脚本中显式打开稳定性/性能开关。
每个开关都要有一组小矩阵结果支持。
```
