## 当前判断

这个卡点不是单纯启动参数问题，而是调度器 admission 与底层实际显存需求不一致：

1. `Scheduler.can_accept_request()` 使用 KV block 数量做 admission。
2. 但底层 forward 还有额外临时显存分配，特别是长上下文 + 多请求 + graph/flash-attn 场景。
3. 调度器认为可调度，底层实际 forward 时 `cudaMalloc` 失败。
4. 失败后 `RankWorker stopped during run`，服务进入 unhealthy。

也就是说，当前需要代码层保护：

```text
不要让 scheduler 组成会触发底层 OOM 的长上下文 batch。
```

## 下一步建议

优先做一个低风险调度保护，而不是继续盲扫参数。

### 方案 A：长上下文 batch cap

在 `python/infinilm/llm/scheduler.py` 中增加策略：

```text
如果本轮 prefill/decode 中请求 total length 很长，则限制 scheduled_requests 数量。
```

例如：

```text
prompt_len >= 4096 时，单 step 最多调度 1 个 prefill 请求。
total_length >= 4096 且 output 较长时，decode batch 上限降低。
```

优点：

- 简单直接。
- 可以避免服务崩溃。
- 先追求 benchmark 完成，再谈吞吐优化。

缺点：

- 长输入并发吞吐会低。
- 但比 unhealthy/timeout 更可接受。

### 方案 B：基于 token budget 的动态 batch

当前已有 `INFINILM_MAX_NUM_BATCHED_TOKENS` 控制 prefill token budget，但 decode 阶段主要按 `max_batch_size` 取 running queue。

可以增加 decode token/length pressure 限制：

```text
decode batch 不只看请求数，也看 total_kv_lengths 总量或 max total length。
```

例如：

```text
sum(req.get_total_length()) <= 某个阈值
```

优点：

- 比固定 long-context cap 更泛化。

缺点：

- 需要多试阈值。

### 方案 C：OOM 后 graceful recovery

当前底层 OOM 会让 RankWorker 停止，服务 unhealthy。可以考虑捕获错误后标记请求失败并恢复 worker，但这涉及底层状态一致性，风险更高。

不建议作为第一步。


代码层逻辑：

1. 当请求 `prompt_len`、`total_len` 或 `prompt_len + max_tokens` 达到阈值时，视为 long-context request。
2. 同一轮 scheduler batch 中 long-context request 数量受 `INFINILM_LONG_CONTEXT_MAX_BATCH` 限制。
3. 当 `INFINILM_DECODE_FIRST_WHEN_RUNNING=1` 且 running queue 非空时，waiting queue 的新 prefill 会被延后，避免长 prefill 和长 decode 交叠造成底层 OOM。

语法验证：

```bash

```

结果：通过。

```text
不能仅通过降低“完整输出预留”来安全提高这个场景的稳态吞吐：请求在生成到后段仍必须占用完整 KV，
没有 KV swap/preemption 时会转化为中途无 block 的风险。后续应优先测试可承受的 KV 容量上限，
或接受该长输出场景的排队代价；不要为此仓促加入不安全的动态预留逻辑。
```
